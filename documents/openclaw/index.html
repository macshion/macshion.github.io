面向个人知识运营与研发自动化的 OpenClaw Operator 学习路线

这是一份详细的OpenClaw学习大纲，按照Operator 使用者的真实成长路径：“认知层 → 架构层 → 安全层 → 操作层 → 自动化层 → 生产化层”来排。

OpenClaw 当前的核心能力确实集中在 Gateway、agents、sandbox、cron、workspace/skills 这些部分，所以这份大纲也会围绕它们展开。

第 1、2、3 章，建立认知和安全底座。
第 4、5、6、7 章，理解系统怎么搭、怎么分角色。
第 8、9、10、11、12 章，把自动化、采集、整理、入库跑起来。
第 13、14、15、16 章，走向稳定运行和长期治理。

第 0 章：学习目标与学习边界

0.1 你为什么学 OpenClaw

先回答这几个问题：
你是想把它当聊天工具，还是执行系统
你是想做本地研发助手，还是内容采集流水线
你希望它是“建议型 Copilot”，还是“执行型 Operator”
你是否接受它周期性自动运行

0.2 你的应用场景定义

这一节专门把你的目标写清楚：
固定格式信息收集与整理
汉字检定资料抓取、抽取、结构化
日常资讯巡检与摘要
课程模块化整理
项目原型验证与快速开发
数据库中间层与受控入库

0.3 不在第一阶段学习范围内的内容

聊天渠道集成
复杂多节点分布式执行
大规模 plugin 生态接入
生产级对外发布与自动发帖
高权限云资源操作

这一章的目标，不是学技术，而是先定义“学什么，不学什么”。

第 1 章：OpenClaw 是什么，它不是什么

1.1 OpenClaw 的定位

不是普通 CLI 工具
不是单纯对话壳
不是只有 terminal access 的 coding agent
它更像本地 agent runtime / operator shell，围绕 Gateway、agent turn、workspace、skills、cron、sandbox 组织能力。

1.2 OpenClaw 的核心思想

模型只负责推理
工具负责行动
Gateway 负责调度和中转
Agent 负责执行具体任务
Workspace 负责隔离上下文与目录
Sandbox 负责环境隔离
Cron 负责定时运行

1.3 Copilot 与 Operator 的区别

建议模式
半自动模式
自动执行模式
为什么你更接近 Operator

1.4 OpenClaw 与其他 agent 框架的差异

与单纯 CLI agent 的区别
与 MCP / tool calling 的区别
与“浏览器自动化 + LLM”的区别
与 IDE 内 Copilot 的区别

1.5 你的认知底座

什么任务适合 agent
什么任务不适合 agent
什么任务一定要人工把关

这一章的目标是建立概念坐标系。你之后遇到任何命令，都会知道它属于哪个系统层次。

第 2 章：整体架构认知

2.1 Gateway 是什么

为什么几乎所有能力都围绕 Gateway 展开
为什么很多 CLI 命令其实是在操作 Gateway
Gateway 在本地运行意味着什么
Gateway 与 agent、cron、logs、health 的关系。官方 CLI 文档也把 gateway 作为运行、检查和查询 WebSocket Gateway 的核心命令。

2.2 Agent 是什么

一次 turn 的概念
agent 和 agents 命令的区别
默认 agent 与隔离 agent 的区别
agent 如何接收指令、调用工具、产出结果

2.3 Workspace 是什么

为什么要分 workspace
workspace 与目录权限的关系
workspace 与 agent 身份的关系
为什么你的采集员、整理员、原型员应分开

2.4 Sandbox 是什么

为什么 sandbox 不是“高级可选项”，而是 Operator 的核心能力之一
Docker sandbox 的意义
什么情况下必须进 sandbox
什么情况下可以先不进 sandbox。官方 docs 明确把 sandbox 作为基于 Docker 的隔离容器管理能力。

2.5 Cron 是什么

定时任务的本质
为什么 cron 适合资讯巡检
为什么 cron 不适合一开始就跑高价值写操作。官方文档说明 cron 由 Gateway scheduler 管理 recurring 和 one-shot jobs，并带有运行记录与失败处理。

2.6 Skills / Plugins / Hooks 的概念边界

什么是 skills
什么是 plugins
什么是 hooks
它们在架构里分别扮演什么角色

这一章的目标是把系统结构“看见”。

第 3 章：Operator 使用者必须建立的安全观

3.1 权限不是功能，权限是风险放大器

读权限
写权限
执行权限
网络权限
账号权限
密钥权限
数据库权限

3.2 信任边界

为什么不应该让一个 agent 同时拥有采集、改写、发出、入库、联网全部能力
为什么高价值任务要拆角色
为什么不同 workspace 应对不同风险级别

3.3 最小权限原则

按任务给权限，而不是按想象给权限
采集员最小权限
整理员最小权限
原型员最小权限
执行员最小权限

3.4 Skills / 插件风险

为什么 skill 生态强大但危险
markdown 指令包为什么可能构成攻击面
为什么第三方 skill 不能盲装
为什么技能管理和来源审计是长期主题。OpenClaw 社区近来就在集中讨论 skills / plugins 的信任、权限和扫描问题。

3.5 Gateway 共享风险

为什么一个 Gateway 不适合跨信任用户共享
为什么官方安全建议强调按信任边界拆分 Gateway，甚至做到一机一用户。

3.6 你的第一阶段安全红线

不碰生产数据库
不碰正式社媒发帖
不碰云资源 root 权限
不碰 SSH 私钥
不让采集 agent 直接入正式库
不让实验 agent 直连正式项目主分支

这一章非常重要。你如果不先学这一章，后面越学越危险。

第 4 章：安装、初始化与运行路径

4.1 安装后的系统目录和 profile 概念

--dev 的意义
--profile 的意义
为什么 profile 是学习和实验的基本手段

4.2 setup / onboard / configure / config 的关系

4.3 Gateway 的启动方式

本地 Gateway
临时启动
健康检查
日志查看
状态检查。官方文档说明 gateway、health、logs、status、doctor 组成了基础运行与排障入口。

4.4 模型配置基础

本地模型 / 远程模型
为什么不同 agent 不一定要用同一个模型
成本、速度、准确率的权衡

4.5 第一次成功运行的最小闭环

能发起一次 agent turn
能拿到结果
能看 logs
能排查失败

7.4 目录权限映射

哪个 agent 能读哪些目录

7.5 你的项目怎么映射到 workspace

第 8 章：Sandbox 学习专题

8.1 Docker sandbox 基本原理

为什么 agent 跑在容器里更安全
容器不是绝对安全
容器更像损害控制手段。官方文档将 sandbox 明确绑定 Docker。

8.2 哪些 agent 必须放进 sandbox

采集员
原型员
带 shell 权限的整理员

8.3 哪些场景可以先不进 sandbox

低风险只读总结

完全受控目录内的小任务

8.4 sandbox 的局限与常见坑

文件挂载
网络连通
环境变量
容器持久化
宿主机差异。官方 issue 和文档都表明 Docker/sandbox 组合存在实际环境边界和配置注意点。

8.5 你的 sandbox 学习目标

知道何时用
知道为什么用
知道怎么排查
知道怎么验证隔离是否生效

这一章是你从“会用”走向“敢用”的关键。

9.6 cron 故障排查
